Recruiting through a panel provider

Demoscopic providers (Bilendi, Dynata, Cint, Toluna and the rest) hand each respondent a single-use identifier in the link they open, and expect the questionnaire to send them back to a return URL carrying that identifier. The return leg is not optional: it is how the provider learns the person finished, and therefore how the person gets paid. A field that collects the token but never bounces the respondent back is unusable.

Token parameter

The name of the query parameter carrying the respondent id. Providers disagree on it, and on its capitalisation, so the match is case-insensitive.

  • Bilendi, Cint — RID
  • Dynata — psid
  • Toluna — tid

Setting this field is what switches panel mode on. Clear it to go back to an open link.

Entry URL

Give the provider the public survey URL with the parameter appended:

https://…/s/{{ slug }}?{{ panel.param or 'RID' }}=[respondent id]

Anyone arriving without a valid token is stopped before the questionnaire and sent to the screenout URL, since a respondent nobody can credit should not spend ten minutes answering. To walk the questionnaire yourself, append ?preview=1 while signed in as the owner; preview submissions are stored but never bounce to the provider.

Return URLs

The provider supplies three, and all three are used:

  • Complete — the respondent finished and should be credited.
  • Screenout — they were turned away, by a consent or eligibility gate, a missing token, or a token already spent.
  • Quota full — their demographic cell is already filled.

The token is appended as ?param=token, or, if the URL contains a {token} placeholder, substituted in place. The placeholder form covers providers whose return URL carries the id mid-path:

https://panel.example.com/end/{token}/done

Routing a respondent who does not complete

The questionnaire decides the outcome by setting a field named _outcome. The usual case is a consent gate, wired with a SurveyJS trigger:

"triggers": [{
  "type": "setvalue",
  "expression": "{consent} empty",
  "setToName": "_outcome",
  "setValue": "screenout"
}]

Accepted values are complete (the default when the field is absent), screenout and quotafull; anything else falls back to complete. The response is stored either way, so refusals and screenouts stay in your data instead of vanishing.

One token, one response

A token that has already produced a response cannot start the questionnaire again, and cannot submit again. This is enforced by a uniqueness constraint in the database rather than by a check before the insert, so two simultaneous submissions cannot slip through.

In your data

The token appears as _panel_token in the CSV, Excel and JSON exports, which is what you reconcile against the provider's delivery file.

A panel token is a pseudonymous identifier: the provider can trace it back to a person. A study recruiting this way should say so in its ethics application and in its participant information, and should not describe its responses as carrying no identifying metadata.

Randomization and files

Randomization — pools

A pool is a set of pages from which each participant is shown a given number. With four pages and a show count of two there are six possible combinations, and each participant gets one. A survey can hold several independent pools at once, for instance one assigning the experimental condition and another varying the order of vignettes; they do not interfere with each other.

Randomization — balanced allocation

Each participant is assigned the combination with the lowest count so far, with ties broken at random. This keeps the arms level without participant-level blocking.

The count is completed responses, not page loads, plus any assignment issued in the last hour so that simultaneous starts do not all land on the same arm. Someone who opens the link and leaves therefore stops affecting the balance once the hour is up. The randomization page shows both figures, as Completed and In progress.

Randomization — condition variable

Available when the show count is 1. Name a variable and the assigned condition is exposed to the questionnaire before it renders, ready for use in visibility rules on any page:

"visibleIf": "{condition} = 'A' or {condition} = 'C'"

The value comes from the optional value map, or is the page name itself when no map is set. A map turns page names into something readable:

{"info_a": "control", "info_b": "treatment"}

Changing a pool's configuration clears its balance history, since the old counts no longer describe the new set of combinations.

Files

Each survey has its own upload folder, so two surveys can hold files of the same name without colliding. Images, PDFs and SVGs are accepted (jpg, jpeg, png, gif, webp, svg, pdf), up to 10 MB each.

An uploaded file is served at a stable path you reference directly from the questionnaire schema:

/uploads/{{ slug }}/diagram.png

Use it in an image question, or in the HTML of any element:

{
  "type": "image",
  "name": "stimulus",
  "imageLink": "/uploads/{{ slug }}/diagram.png"
}

The reference data shipped with the platform (cantons and countries, in EN, DE, FR and IT) is uploaded the same way and can then be reused across surveys, which is how a country drop-down gets its options without hard-coding them into every schema.
