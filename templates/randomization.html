How randomization works

Pool

A pool is a set of survey pages from which the system selects one or more to show each participant. You can have multiple independent pools in the same survey — each runs its own balanced assignment.

Show N page(s)

How many pages from the pool each participant sees. With 4 pages and Show = 2, there are 6 possible combinations. Each participant is assigned one combination.

Balanced allocation (minimization)

The algorithm always assigns the combination with the lowest count so far. Ties are broken randomly. This keeps exposure counts as balanced as possible without pure randomization — no participant-level blocking needed.

The count that drives the balancing is completed responses, not page loads, plus any assignment issued in the last hour so that simultaneous starts do not all land on the same combination. A participant who opens the link and leaves therefore stops affecting the balance once the hour is up, which matters most with panel traffic, where abandonment is high. The In progress column shows the assignments currently counted but not yet submitted.

Condition variable

Only available when Show = 1. Set a name here (e.g. condition) and the system will expose that variable in the survey before it renders — so you can use it in visibleIf expressions on any page:

"visibleIf": "{condition} = 'A' or {condition} = 'C'"

The value is taken from the Value map if provided, or is the page name itself if not.

Value map

Optional JSON that translates page names into readable condition values. Without it, the raw page name becomes the value. Example:

{"info_a": "A", "info_b": "B", "info_c": "C"}

Or with meaningful names:

{"info_a": "control", "info_b": "treatment"}

Page order

Optional JSON that changes the order in which pages appear, for one condition value. Only available when Show = 1 and a condition variable is set. Use it to counterbalance presentation order: a pool assigns the condition, and this map decides which page comes first.

{"GGE_FIRST": ["vignette_gge", "vignette_pgt"]}

The named pages are put back into the positions they already occupy in the schema, in the order listed — nothing else moves, and pages not named are untouched. A condition value with no entry keeps the schema order, so only the reversed arm needs listing.

This exists so that counterbalancing does not require duplicating pages: duplicated pages would mean duplicated question names, and the same answer landing in two different columns depending on the arm.

Multiple pools

Each pool is independent. A survey can have a pool for condition assignment (Show = 1, with condition variable) and a separate pool for vignette order (Show = 2, no condition variable) — they run simultaneously and don't interfere.

Saving a pool resets its counters

Any configuration change resets the assignment counts for that pool. Use Reset to clear counts without changing the configuration.

How item banks work

The editor

Each bank opens in a visual editor; Edit as JSON shows the same configuration as text, which the editor reads back when you return. Findings come from the server while you edit, and the panel on the right shows an example draw per group. Generate pages from a table, under Content, writes one version page per row of a pasted table from a template page with {{placeholders}}. Under Groups, Rotation across waves adds to the questionnaire the calculated value that gives each participant the next group at each wave.

Items and versions

An item is a unit of content; a version is one rendering of it, and each version is a page of the schema. Each version keeps its own question names, so an answer always lands in a column that says which item and which version it belongs to.

[{"item": "P001", "versions": {"H": "P001_H", "L": "P001_L"}}]

Propose from page names builds this list from the schema, with a regex whose groups item and version split each page name. Pages that do not match are listed so nothing is left out unnoticed.

What a participant gets

First an arm, then Show items, one version of each, in random or schema order. The pages of the bank that were not drawn are hidden; nothing else moves. A bank never shows two versions of the same item to the same person.

Arms

Optional. Each arm is a quota of versions that sums to Show:

[{"name": "LLM30", "quota": {"H": 7, "L": 3}},
 {"name": "LLM70", "quota": {"H": 3, "L": 7}}]

The drawn arm is exposed under the arm variable, like a pool's condition, so it can drive visibleIf anywhere in the survey. Without arms, each item gets the version it has been shown in least.

Balance

The least-used arm is drawn, then the least-shown items, then versions are assigned so that each item moves toward an even split across its versions while the arm's quota is met exactly. As for pools, the count that drives this is completed responses plus draws issued in the last hour.

Pages and questions

A page belongs to at most one bank, and never to a bank and a pool. Name the questions on a version page <page>_<role> (P001_H_quality): the long export strips the page name and lines the answers up by role across versions.

Data

Each response records what it was shown — arm, items, versions, pages — from the server's own ledger, so the record survives a deleted bank. Long export on the survey page gives one row per response and drawn item, the table a mixed model wants.

Saving resets the draws

A balance computed under another configuration means nothing, so saving starts it again. Reset clears the draws without changing the configuration.
